# 02 — Multimodal RAG

RAG over a corpus that mixes markdown text and images, with real pixels re-attached to the generation call.

Most "multimodal RAG" write-ups either skip retrieval entirely (just stuff every image into context) or fake it by only ever indexing text. This starter does the real pattern: images are captioned once at ingest time so they're searchable through the same hybrid text index as everything else, and at query time the top-ranked *image* items are re-attached as actual base64 image content blocks — the model answers from real pixels, not from its own caption.

## What it does

- Ingests a directory of `.md` files and `.png` images into one unified index.
- Images are captioned by Claude vision (or, offline, by a stub that genuinely decodes the PNG's pixels — real width/height and two real color statistics, mapped to the nearest named color). Captions are cached to disk keyed by a SHA-256 of the image bytes, so re-ingesting doesn't re-pay for vision.
- Text and image captions are chunked/indexed together with the same hybrid BM25 + dense + RRF retrieval as `01-basic-rag`.
- At query time, retrieved image items are loaded from disk and sent to Claude as real `{"type": "image", "source": {"type": "base64", ...}}` blocks; retrieved text items are sent as text. The model never sees a caption standing in for an image it could see directly.
- Citations resolve `[n]` markers back to real item ids and source filenames (text or image), same as `01-basic-rag`.

## Architecture

```mermaid
flowchart LR
    subgraph Ingest
        T[data/corpus/*.md] --> C1[chunk_corpus]
        I[data/corpus/images/*.png] --> V[caption_image\nAnthropic vision or PNG-pixel stub]
        V --> CC[(caption cache\nkeyed by sha256)]
        C1 --> IDX[Unified Index JSON\ntext chunks + image items]
        V --> IDX
    end
    subgraph Query
        Q[question] --> HS[hybrid_search\nBM25 + dense + RRF]
        IDX --> HS
        HS --> TOPK[top_k items]
        TOPK -->|text item| TB[text content block]
        TOPK -->|image item| IB["read file -> base64\nimage content block"]
        TB --> GEN[Claude generate_answer]
        IB --> GEN
        GEN --> ANS[answer with \[n\] markers]
        ANS --> RES[resolve_citations]
        TOPK --> RES
    end
```

## When to use it

Use this when your corpus genuinely mixes text and images (reports with embedded charts, hardware docs with schematics, inspection photos with notes) and you want one search that finds either kind and grounds the answer in the real image when that's what's relevant.

Don't use it as-is for: large image collections (vision-captioning cost scales linearly with images, even though it's cached); PDFs (deliberately out of scope — see Limitations); or cases needing real semantic image search (this indexes *captions*, not learned image embeddings, so a visually-similar-but-differently-described image won't be found).

## Prerequisites

- Python 3.11+
- [`uv`](https://docs.astral.sh/uv/) (or `pip`)
- No API key needed to run the offline demo. An `ANTHROPIC_API_KEY` enables real vision captioning and generation.

## Setup

```bash
cd starters/02-multimodal-rag
uv venv --python 3.13
uv pip install -e ".[dev]"
cp .env.example .env   # optional: add a real API key later
```

## Environment variables

| Name | Required? | Default | What it is for |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | No | unset | Enables real vision captioning (ingest) and real generation (query). Without it, both fall back to the offline stub (logged). |
| `ANTHROPIC_MODEL` | No | `claude-opus-5` | Model id used for captioning and generation. |
| `VOYAGE_API_KEY` | No | unset | Enables real semantic embeddings instead of the hashing embedder. |
| `LLM_PROVIDER` | No | `anthropic` | `anthropic` or `stub`. Forces the backend regardless of API key presence. |
| `LOG_LEVEL` | No | `INFO` | JSON line logger level. |
| `TOP_K` | No | `5` | Default chunks/items retrieved per query. |
| `RRF_K` | No | `60` | Reciprocal Rank Fusion constant. |

## Run it

Offline, no API key, using the bundled sample corpus (4 synthetic chart/schematic PNGs + 3 markdown docs describing them):

```bash
cd starters/02-multimodal-rag
uv run multimodal-rag ingest --offline
uv run multimodal-rag query "Which chart is mostly blue?" --offline
uv run multimodal-rag query "Describe the pipeline schematic" --offline --top-k 8
```

With a real Claude key (paid calls: one vision call per *uncached* image at ingest, one generation call per query):

```bash
uv run multimodal-rag ingest
uv run multimodal-rag query "Which chart is mostly blue?"
```

Regenerate the sample images (stdlib-only PNG writer, no dependencies):

```bash
python data/make_samples.py
```

## Example input

```bash
uv run multimodal-rag query "Which chart is mostly blue?" --offline --top-k 8
```

## Expected output

Real, trimmed output from the command above:

```
[stub] Grounded answer for: 'Which chart is mostly blue?' (text 01-chart-notes.md) In every chart, three
bars share the quarter's main color and one bar is an accent color... [1] (text 01-chart-notes.md)
`chart_q1_blue.png` is a small bar chart, drawn in mostly blue bars with one orange accent bar... [2]
(image) chart_q1_blue.png [7]

Retrieved:
  [7] (image) chart_q1_blue.png

Citations:
  [7] -> chart_q1_blue.png (item 0a1e6caedc7f)
```

At the default `--top-k 5`, this small corpus's verbose text chunks about the charts usually outrank the
shorter image caption — the image genuinely is in the index and is retrievable (as shown above with
`--top-k 8`), it just isn't always the single highest-scoring item. That's an honest property of a small
demo corpus with BM25-heavy hybrid search, not a bug — see Limitations.

## How the flow works

- **Captions drive retrieval; pixels drive the answer.** `caption_image` runs once per unique image (cached by content hash) and produces searchable text. That text is what BM25/dense retrieval matches against. But when an image item is actually selected for the answer, `generation.py` reads the *original file* and sends real pixels — the caption never substitutes for the image in the final answer.
- **The offline stub genuinely decodes pixels.** `images.py` implements PNG un-filtering (all 5 filter types) from scratch against the raw IDAT stream — no Pillow, no numpy image ops — then computes the actual dominant color and dominant non-background color, mapped to the nearest of 12 named colors by Euclidean distance. This is real (if crude) image understanding, not a placeholder string.
- **One index, two content kinds.** `Item.kind` is `"text"` or `"image"`; both flow through the same `chunking`/`bm25`/`embeddings`/`retrieval` pipeline as `01-basic-rag`, so adding image support didn't require a second retrieval system.

## Extension ideas

- Swap the hashing embedder for a real multimodal embedding model and compare retrieval quality.
- Add a re-ranking pass after RRF that boosts image items when the query contains visual language ("chart", "photo", "diagram", a color name).
- Add JPEG support to the offline pixel decoder (currently PNG-only; JPEG falls back to dimensions-only captioning via `Pillow`, which isn't a dependency here).

## Limitations

- **No PDF support.** The Anthropic `document` content block (base64 PDF) is straightforward to add, but this starter intentionally ships only PNG images to keep the stdlib-only offline decoder honest and complete rather than half-implemented. Add a `document` block in `generation.py` following the same pattern as the image block if you need it.
- **Offline captions are pixel statistics, not content understanding.** The stub cannot read a chart's axis labels or a schematic's box labels — only dimensions and two dominant colors, named via a small fixed 12-color palette. Real vision captioning (with an API key) reads actual content.
- **PNG decoder supports 8-bit RGB/RGBA only** — no palette (indexed), 16-bit, or interlaced PNGs. `data/make_samples.py` only ever produces the supported kind, so the bundled sample data always works.
- Same corpus-size and access-control limitations as `01-basic-rag` (in-memory JSON index, no per-document ACLs).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `EmbedderMismatchError` on query | Index was built with a different embedder than the query is using (e.g. built with Voyage, queried `--offline`) | Re-run `ingest --offline` (or without `--offline`) to rebuild the index with a matching embedder |
| Image never appears in results at small `--top-k` | Verbose text chunks outrank short image captions on this small corpus (see Expected output) | Raise `--top-k`, or ask a question closer to the image's caption vocabulary |
| `ingest` says "offline pixel-color inspection only supports 8-bit RGB/RGBA PNGs" | The PNG is palette-indexed, 16-bit, or interlaced | Only relevant for images outside the bundled sample set; re-export as 8-bit RGB/RGBA PNG |

## Production hardening

- Replace the JSON index with a real vector store (pgvector, Qdrant) once the corpus outgrows an in-memory scan.
- Add a virus/format scan on uploaded images before decoding.
- Cap total image bytes sent per generation call (base64 images consume real input tokens).
- Add per-document access control if the corpus is multi-tenant.
